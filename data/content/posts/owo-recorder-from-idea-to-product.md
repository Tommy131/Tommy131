OwO! Recorder 最开始并不是一个完整产品，而是一个很具体的想法：如果我在德语或英语课堂上听不懂某句话，能不能让电脑帮我把老师说的话实时转成文字和中文，同时把课堂内容保存下来，课后继续复习？

这个想法看起来像“录音加翻译”，真正开始实现之后才发现，它同时涉及浏览器音频采集、实时通信、语音识别、机器翻译、本地模型运行、数据保存、任务恢复和硬件兼容。项目也因此从一个小工具逐渐变成了一套本地优先的课堂学习系统。

这篇文章先记录项目为什么开始、最初如何落地，以及它后来为什么不断改变架构。后续文章会再分别展开实时转录、模型运行、测试和具体问题排查。

## 起点：课堂里缺少一个可靠的辅助工具

对留学生来说，课堂理解通常不是把一句话翻译出来这么简单。老师可能连续讲几分钟，使用专业术语、缩写和上下文引用。只看某一个单词的翻译，解决不了“这一段到底在讲什么”的问题。

我希望这个工具至少能完成四件事：

- 录下经过用户明确授权的麦克风或系统声音；
- 把课堂内容转成原文，并在适用时翻译成中文；
- 在课堂结束后生成可以复习的重点、术语和问题；
- 让音频、文字和分析结果尽量留在自己的设备上。

最后一点很重要。课堂录音可能包含老师、同学和课程资料，不能默认把它们上传给第三方模型服务。因此项目从一开始就采用“本地优先”的方向：识别、翻译、分析和总结由用户自己的设备完成，服务器只负责必要的同步、存储和运维能力。

## 最初的产品模型

第一版的核心流程很简单：

```text
浏览器采集音频
    -> 本地或受控后端缓存
    -> 语音识别为原文
    -> 翻译为中文
    -> 生成课堂重点和学习资料
    -> 保存并导出
```

最初我并不打算做账号系统、多人协作或商业化计费，也没有把目标定成商业级同声传译。第一阶段更重要的是证明一条完整链路可以工作：从开始上课，到看到实时文本，再到课后拿到可以复习的资料。

技术上，前端使用 React、TypeScript 和 Vite，后端使用 Python、FastAPI 和 SQLite。浏览器通过 WebSocket 发送音频分片，后端连接本地的语音识别、翻译和分析模型。录音、转写、翻译和学习资料都保存到本地数据目录中。

这个选择也保留了足够的调整空间。模型可以替换，前端可以独立构建，数据库可以继续作为权威数据源，长任务也可以从请求生命周期中分离出来。

## 第一次真正落地：先让完整流程跑起来

项目早期的重点不是把每一个模块做得完美，而是先完成一次完整的课堂流程：

1. 用户选择课堂语言和录音来源。
2. 浏览器请求麦克风或系统声音权限。
3. 音频被转换成固定格式的 PCM 分片并通过 WebSocket 发送。
4. 服务端把音频交给 ASR 模型生成原文。
5. 原文被翻译成中文，并在页面上显示。
6. 课堂结束后，后台继续完成总结和学习资料生成。
7. 用户可以回放录音、查看双语内容并导出 Markdown。

这一步暴露出一个事实：实时页面只是系统的一部分。真正有价值的结果不是某一行即时字幕，而是课堂结束之后仍然可以检索、复习和重新处理的内容。因此项目很快从“实时翻译工具”扩展成“课堂资料工作区”。

## 从实时字幕到学习资料

课堂结束后，用户需要的不只是完整转写。项目后来加入了总结、关键要点、术语和复习问题，并把学习资料作为版本保存。这样重新分析时不会直接覆盖以前的结果，用户也可以比较不同版本。

这改变了数据模型的设计。音频、转写、翻译、分析和导出文件之间需要有明确的版本关系；重新转写成功后，旧的分析结果不能继续假装对应新的文本；某一步失败时，也不能把已经完成的资料一起清空。

因此，SQLite 成为权威数据源，JSONL 和 Markdown 等文件作为可以重建的本地缓存或导出结果。每一个长任务都需要记录状态、进度、失败原因和是否可以继续，而不是简单地等待一个 HTTP 请求返回。

## 现实问题让架构不断变化

当项目开始处理真实课堂时，原本隐藏的约束逐渐出现了。

实时识别不是把音频交给模型就结束了。音频需要切窗，窗口之间需要重叠，服务端要处理确认回执、断线重发、重复内容和句子边界。翻译如果占用唯一的处理队列，下一段 ASR 就可能被阻塞。一个识别窗口如果失败后已经从缓冲区删除，课后最终稿也可能永久缺少这一段。

长课堂又带来了模型输入长度问题。整节课不能一次性塞进最终分析模型，于是项目增加了分段、检查点和分层归并，让长文本可以按音频或转写边界分解，再逐步生成最终资料。暂停、停止、重启和重试都要保留已经成功完成的部分。

模型运行本身也不稳定。不同显卡的显存、CUDA 能力、操作系统和 Python 环境都不一样。项目不能在 CUDA 失败时悄悄退回 CPU，然后让用户误以为性能仍然可靠；启动器需要检查环境，计算节点需要安装受约束的运行库，并在安装失败时恢复旧环境。

## 从单机模型到私有计算节点

随着功能变多，单机服务端同时承担网页、API、录音存储和模型推理变得越来越难维护。于是项目引入了私有计算节点：用户可以把自己的另一台电脑绑定到系统，由这台设备运行 ASR、翻译和分析模型。

这个变化没有改变本地优先的原则，反而把它表达得更清楚：课堂模型可以运行在用户自己的另一台电脑上，服务器保存课堂状态并负责调度，但不会把课堂内容发送给第三方推理平台。

计算节点还带来了新的工程问题：节点配对、心跳、断线重连、任务确认、队列容量、GPU 选择、客户端更新和不同平台的启动方式。原来的“调用一次模型”变成了一个需要恢复和观测的分布式任务。

## 隐私要求最终影响了整个系统

本地优先不是 README 里的一句宣传语，它会影响每一层实现：

- 日志不能记录原始音频、课堂文字、提示词或模型输出；
- API 需要区分用户、设备、课堂和录音的所有权；
- 公网浏览器不能直接访问无认证的内部 API；
- WebSocket 需要认证、来源校验和有限的背压窗口；
- 分享链接必须是可撤销的，并且默认不包含音频；
- 删除录音时需要同时处理文件、元数据、派生结果和审计记录。

这也是项目后来增加 BFF、认证、所有权边界、存储配额和审计设计的原因。它们并不是与录音功能无关的附加模块，而是把本地数据带到受控远程环境时必须面对的边界。

## 现在的 OwO! Recorder

经过多轮实现和修复，项目已经具备了比最初想法更完整的形态：

- 支持麦克风和浏览器授权的系统声音采集；
- 支持多种课堂语言、原文转写和中文翻译；
- 支持实时字幕、课堂要点和课后学习资料；
- 支持录音回放、Markdown 导出和重新处理；
- 支持长课堂的可恢复分析和资料版本；
- 支持私有计算节点和不同操作系统、GPU 的运行环境；
- 支持认证、数据所有权、分享链接、存储和运维管理。

它仍然有明确限制：本地模型需要足够的硬件，系统声音采集受浏览器权限约束，首次初始化可能需要下载模型和运行库，数据备份也仍然需要用户自己负责。

## 回头看，项目真正解决的是什么问题

如果只看功能列表，OwO! Recorder 像是录音、转写、翻译和总结的组合。但开发过程中我逐渐意识到，它真正要解决的是“如何把一段不容易理解的课堂内容，可靠地变成可以复习的个人资料”。

实时字幕解决的是当下的理解，录音和转写解决的是事后的回看，翻译和术语解释解决的是语言门槛，版本化学习资料解决的是长期复习。它们必须在同一条可靠的数据链路上协同工作。

这个项目也让我重新认识到，AI 应用的难点往往不只在模型效果。音频是否丢失、任务是否可恢复、结果是否属于正确的用户、失败时能否给出明确反馈，以及系统是否真的尊重用户数据，同样决定了产品能不能被长期使用。
