第一篇文章记录了 OwO! Recorder 为什么开始，以及它如何从课堂翻译的想法逐步变成一套学习资料系统。这一篇继续往下拆，看看项目现在的各个部分如何协作。

我把当前架构称为“本地优先”，但它不是简单地把所有代码都塞进一台电脑。更准确的说法是：课堂模型和课堂内容尽量留在用户控制的设备上；服务端只承担身份、状态、同步、存储和受控调度等职责；每一层都明确自己拥有的数据和权限。

## 先看一条完整链路

一次课堂从开始到结束，大致经过下面这些环节：

```text
浏览器
  -> 采集麦克风或系统声音
  -> 转换为 PCM 音频分片
  -> 通过认证后的实时连接发送

Recorder API / BFF
  -> 接收分片并保存课堂状态
  -> 安排识别、翻译和分析任务
  -> 持久化结果和进度

用户自己的计算设备
  -> ASR 识别原文
  -> 翻译为中文
  -> 生成课堂要点和学习资料

浏览器
  -> 展示实时结果
  -> 读取课后资料、回放录音和导出文件
```

这条链路里，浏览器不是模型运行环境的替代品，服务器也不是一个无限资源的 AI 黑盒。每一个环节都需要处理失败、重试、断线和权限问题。

## 浏览器只负责采集和展示

前端的首要工作是向浏览器请求用户明确授权的音频来源。它可以是麦克风，也可以是浏览器共享选择器提供的系统声音。系统声音不是应用可以偷偷读取的设备，用户必须在共享对话框中明确选择音频轨道。

采集到的音频会被转换成固定格式的 16 kHz、单声道 PCM16 分片。固定格式让后端和模型适配器更容易处理，也让确认、重发和时长统计有统一基础。

浏览器端还维护有限的待确认队列。服务器确认以前，音频不能立刻从客户端缓存中删除；连接短暂中断时，客户端需要根据确认位置继续发送缺口。这个设计的目标不是让网络永远可靠，而是让短暂的网络问题不会静默变成录音缺失。

前端只渲染服务端确认的结果。它不会自己猜测一句话什么时候结束，也不会把尚未被服务器接受的文本当成最终转写。这样虽然需要更多状态处理，但可以避免页面显示的内容和数据库最终保存的内容不一致。

## API 和 BFF 的职责不同

项目目前把浏览器访问和内部处理拆成两层。Recorder API 管理课堂、录音、任务和模型处理；BFF 负责浏览器会话、OIDC 登录、Cookie、CSRF、Origin 检查和向内部 API 转发请求。

生产环境中，API 保持在回环地址，公网只到达 TLS 反向代理和 BFF。浏览器不会直接访问没有浏览器认证契约的内部接口，也不会把高权限 Bearer Token 放进前端代码。

这种分层看起来比“前端直接请求 API”复杂，但它解决了几个实际问题：

- 认证流程不需要由每个页面组件自己处理；
- 浏览器只接触同源的受控入口；
- 内部 API 可以保持清晰的服务间契约；
- WebSocket 连接可以在建立时检查登录状态、Origin 和课堂所有权；
- 日志可以分别记录浏览器请求和内部任务，而不记录课堂内容。

本地开发仍然可以使用一体化启动方式，便于快速验证。生产部署则明确关闭内部 API 的前端托管能力，避免把本地开发假设带到公网。

## SQLite 是状态真相，文件是内容载体

课堂系统同时处理结构化状态和大块内容。课堂的语言、状态、任务进度、录音元数据和结果版本适合放在 SQLite 中；录音、导出文件和可重建的缓存则保存到文件系统。

数据库记录的是“现在系统认为发生了什么”，文件保存的是“对应的实际内容”。两者不能互相替代。只保存 JSON 会让并发更新和恢复变得困难，只保存数据库 BLOB 又会让音频读取、备份和磁盘管理变得笨重。

因此，删除一个课堂也不是只删一行记录。系统需要先停止或等待仍在运行的任务，再删除录音、导出和派生资料，最后更新索引并写入不包含课堂内容的审计事件。

## 实时路径和课后路径分开

课堂实时体验最在意延迟，课后整理最在意完整性。两者使用同一份课堂数据，但不应该共用完全相同的调度策略。

实时路径需要尽快完成：

```text
音频分片 -> ASR -> 原文句子 -> 翻译 -> 实时展示
```

课后路径则允许花更长时间处理：

```text
已保存录音和转写
  -> 重新转写或重新翻译
  -> 分段分析
  -> 汇总和资料版本
  -> 导出 Markdown
```

课堂结束后，浏览器音频采集会立即释放，但最终整理可以在后台继续。用户刷新页面时，看到的是服务端保存的任务状态，而不是某个浏览器标签页里的临时变量。

这也是为什么项目需要暂停、继续、停止和恢复。一个长任务不能只依赖一个没有持久化状态的异步函数；已经成功的步骤要能复用，失败步骤要能给出明确原因，重新运行也不能混用不同版本的输入。

## 模型适配器不应该绑死业务流程

ASR、翻译和分析模型的输入输出不同，运行环境也可能不同。项目把它们放在独立的模型服务和适配器边界内，业务层只关心“转写这一段”“翻译这句话”或“分析这些已确认内容”。

这样做有三个好处：

1. 可以替换模型，而不必重新设计课堂、录音和导出流程。
2. 可以在没有真实模型的情况下，用假适配器测试任务恢复、错误映射和状态转换。
3. 可以针对不同设备选择 CUDA、CPU、MPS 或其他明确支持的运行配置，而不是在失败时悄悄切换。

模型选择不是越大越好。实时 ASR 需要低延迟，翻译需要稳定的句子上下文，课后分析则更关心长文本和结构化输出。项目会根据设备能力、显存和任务类型分别安排它们，而不是让所有模型争抢同一个资源池。

## 私有计算节点是本地优先的延伸

当一台电脑同时负责浏览器、数据库和多个模型时，硬件很容易成为瓶颈。项目后来增加了私有计算节点，让用户可以绑定自己的另一台电脑来运行模型。

私有节点不是一个公共云 GPU。它只处理所属用户被授权的课堂任务，服务器负责调度和确认结果，课堂模型仍然在用户控制的设备上运行。节点离线时，系统应该显示等待或不可用，而不是假装任务已经完成。

节点协议因此需要处理：

- 一次性配对和可撤销的设备身份；
- 心跳、断线和自动重连；
- 任务发送、执行和结果确认；
- 队列容量和实时任务优先级；
- 不同操作系统、Python 版本和 GPU 能力；
- 环境安装失败后的回滚和模型完整性检查。

从代码角度看，这已经接近一个小型分布式系统。它提醒我，所谓“本地运行”不代表不需要网络协议，只是网络的边界和所有权更加明确。

## 隐私设计必须落到细节

本地优先最容易被误解成一句产品口号。真正实现它，需要在每个边界做选择：

- 日志只保存请求、任务和结果状态，不保存原始音频、课堂文字、提示词或模型输出；
- API 返回录音元数据时不暴露本地文件路径和内部校验细节；
- 分享链接只返回用户选择的范围，默认不包含音频；
- 账号、设备、课堂和录音之间必须有明确的所有者关系；
- 云端存储和模型推理是两个不同概念，购买存储空间不等于把课堂交给云模型处理。

这些规则会影响数据库字段、API 错误码、日志格式、反向代理配置和删除流程。隐私不是最后补一份说明文档，而是架构的输入条件。

## 当前架构的取舍

这套架构并不追求最少的进程或最短的代码。它选择了更多边界来换取几件事：

- 实时录音不会因为课后分析变慢而完全失去响应；
- 任务可以在刷新、短暂断网或节点重连后恢复；
- 模型可以随着硬件和平台变化而替换；
- 用户可以明确知道课堂内容在哪里处理、由谁拥有；
- 生产公网入口不会直接暴露内部处理服务。

代价也很明确：部署更复杂，测试范围更大，硬件兼容性更难保证，开发时需要维护更多状态。对一个只想做演示的项目来说，这些可能过度；但对要在真实课堂里连续运行几十分钟甚至几小时的工具来说，可靠性比一个漂亮的模型调用示例更重要。

## 下一步要继续解决什么

架构落地以后，最值得继续写的就不再是“用了哪些库”，而是这些边界在真实运行中如何失效：实时转录为什么会丢词，翻译任务为什么会堵住下一段识别，长课堂如何在模型输入受限时完成总结，以及测试怎样证明这些行为不会回归。
