前两篇文章分别介绍了 OwO! Recorder 的起点和本地优先架构。这一篇进入最核心、也最容易被误解的部分：一段课堂声音到底是怎样从浏览器走到用户眼前的字幕的。

表面上，这条链路像是“录音 -> 识别 -> 翻译 -> 显示”。实际运行时，它更接近一组相互独立但必须协作的状态机：浏览器负责采集和有限缓存，WebSocket 负责传输，服务端负责确认和持久化，ASR 负责识别窗口，翻译负责补充结果，前端最后只渲染服务端确认的事件。

## 一条实时课堂链路

当前流程可以抽象成这样：

```text
浏览器音频设备
    -> AudioWorklet
    -> 16 kHz 单声道 PCM16
    -> 客户端待确认队列
    -> 同源 WebSocket /api/v2/sessions/{id}/live
    -> BFF 会话和来源校验
    -> Recorder API 接收、落盘、ACK
    -> 服务端 ASR 缓冲和识别窗口
    -> 原文句子与翻译结果
    -> sentence_result
    -> 浏览器字幕和课堂面板
```

这里有两个容易混淆的“完成”：`audio_ack` 表示服务器已经接受了这一块音频，`sentence_result` 才表示处理链路产出了可以展示的句子。前者是传输确认，后者是模型结果。它们之间可能隔着识别、过滤、翻译和排队。

## 浏览器先把音频变成统一格式

浏览器提供的麦克风和系统声音并不保证采样率、声道数或帧大小一致。项目使用 `AudioWorklet` 建立音频图，把输入送进 PCM16 重采样工作单元，最终输出固定格式的 `Int16Array`。

统一格式有两个实际好处。第一，后端不需要在每个音频分片上猜测编码；第二，时长和缓存大小可以直接根据采样数计算。当前实时协议使用 16 kHz、单声道、PCM16，客户端每次收到一块样本后交给传输层。

AudioWorklet 的输出不会直接播放给用户。工作单元连接到增益为 0 的监控节点，再连接到 `AudioContext` 的 destination。这样既能保持浏览器音频图完整，又不会把正在采集的声音回放到扬声器造成啸叫。

录音控制还需要处理几个浏览器细节：开始时加载 worklet 模块，暂停时挂起 `AudioContext`，恢复时继续，结束时断开所有节点并关闭上下文。关闭过程也要能处理某个节点断开失败，否则下一次课堂可能会继承上一次残留的音频图。

## 分片发送，而不是把整节课放进内存

采集层输出的是连续样本，传输层把它们包装成带元数据的 JSON 文本帧：

```json
{
  "type": "audio_chunk",
  "session_id": "session-id",
  "chunk_id": "session-id:42",
  "audio_format": "pcm16",
  "sample_rate": 16000,
  "channels": 1,
  "payload_base64": "..."
}
```

当前协议使用 Base64 承载 PCM 字节，所以它不是最省带宽的格式，但实现边界清晰，适合早期版本和本机兼容路径。`chunk_id` 由客户端生成，并且在重连重发时保持不变。服务器可以根据这个 ID 判断一块音频是否已经处理过。

客户端不会在 `send()` 成功后立刻删除音频。每一帧都进入待确认队列，只有收到对应的 `audio_ack` 才从队列中移除，并累计服务器确认的音频时长。

```json
{
  "type": "audio_ack",
  "session_id": "session-id",
  "chunk_id": "session-id:42",
  "accepted_audio_ms": 100,
  "duplicate": false
}
```

如果网络中断，待确认队列会保留原始帧；重新连接后，传输层重新发送这些帧。服务器返回 `duplicate: true` 时，客户端仍然把它视为成功，因为这说明服务器已经接受过这块数据，客户端不应该为了“避免重复”重新生成另一个 ID。

## ACK 是背压的起点

实时音频最危险的情况不是 WebSocket 立即报错，而是发送看起来成功、确认却越来越慢。如果客户端无限制排队，内存会持续增加，页面最终只能暂停采集，甚至丢掉尚未确认的音频。

因此传输层维护一个有限的样本预算。默认上限按约 120 秒 PCM 计算。达到上限时，状态变成 `overflow`，页面可以停止继续向队列写入，并提示用户当前处理已经落后。

这个状态和用户主动点击“暂停”必须区分。背压表示系统需要时间追上音频，用户暂停表示用户明确结束当前采集。两者如果共用一条服务端语义，服务器可能会取消正在运行的识别任务，导致已经发送的音频无法继续处理。

连接也不是一次性的。传输层会以递增延迟尝试重连，并定期发送 ping，避免安静课堂中的 NAT 或反向代理把连接当成空闲连接清理。重连成功后，队列中的未确认分片按原顺序重放。

## 服务端先接受，再处理

服务端收到分片后，需要先完成几件事：校验会话 ID、音频格式和 Base64 内容，计算实际时长，把音频追加到录音缓存，并把 PCM 放进当前课堂的 ASR 缓冲。

这一步的顺序很关键。音频已经进入服务端后，ACK 就不应该继续等待完整的模型推理、配额扫描或长时间的录音文件编码。当前实现把录音分段归档和配额检查安排到后台，尽量让接收路径保持短而稳定。

服务端返回的 `accepted_audio_ms` 是累计确认时长，不是字幕延迟，也不是模型完成进度。页面可以用它判断客户端还有多少未确认音频，但不能用它推断“老师刚说的内容已经显示出来”。

## ASR 不是每个分片调用一次

单个 100 毫秒左右的音频分片太短，无法稳定判断句子边界。服务端会把它们追加到 `asr_buffer`，达到完整识别窗口后再调度 ASR。当前配置中的完整窗口约为 5 秒，同时保留上一窗口末尾约 1.5 秒的重叠。

重叠的目的，是给跨窗口的词第二次机会。一个单词或短句刚好落在窗口边界时，下一窗口可以同时看到前一段的尾部和新的声音。但重叠也会带来重复文本，所以服务端还要在窗口结果上做边界裁剪和重复处理。

浏览器不负责判断一句话结束。它只负责发送音频和渲染服务端事件。句子边界由后端根据标点、语义、时长和长度限制决定，事件中可以带上 `boundary_signal`，例如 `punctuation`、`semantic`、`duration_limit` 或 `flush`。

## 为什么要区分预览和正式结果

为了让用户更早看到内容，系统可以在完整窗口准备好以前生成较短的预览。预览用于降低等待感，但它不一定进入最终 transcript，也不能阻塞正式识别窗口。

这带来一个调度原则：正式 ASR 优先于预览，翻译和实时要点不能无限占用唯一的模型工人。否则页面虽然有很多“处理中”，真正负责确认句子的任务却一直排队。

正式结果经过语言检查、重复处理和句子边界判断后，才会发布 `sentence_result`。只有最终事件进入持久化的句子列表，临时预览可以被后续正式结果替代。

## 原文先到，翻译随后补上

识别和翻译不是一个不可分割的同步函数。原文句子一旦被后端确认，就可以先展示；翻译结果随后补充到相同的句子上下文中。这样课堂页面至少能先告诉用户“听到了什么”，而不是在翻译模型变慢时一直显示空白。

如果翻译失败，系统保留原文，并把翻译状态标记为可恢复的失败或源文回退。对于中文课堂，系统直接走“只转写、不自动翻译”的路径，不为了满足统一的 UI 形状创建一条虚假的翻译结果。

这也是实时界面需要多个状态的原因：句子可能是正在识别、已确认原文、正在翻译、翻译完成、源文回退或最终失败。把它们压成一个 `loading` 布尔值，会让用户无法判断系统是在工作、排队还是已经丢失了结果。

## 停止不是立刻杀掉所有任务

用户点击停止时，浏览器先停止音频采集并 flush worklet 中剩余的样本。传输层等待待确认分片排空或达到明确超时，服务端再把会话交给最终整理。

最终整理会继续使用已经保存的音频、转写和翻译。实时 WebSocket 断开不等于课堂失败，也不等于最终分析完成。页面刷新之后，应该重新读取服务端的会话、句子和任务状态，而不是用旧的浏览器内存覆盖服务器状态。

暂停和恢复也是服务端状态的一部分。用户主动暂停时，采集可以挂起；恢复后，连接和缓冲需要继续使用同一个课堂上下文。重连时，服务端仍然根据所有权和会话状态判断这条连接能否继续写入，客户端不能只凭一个本地布尔值自行恢复。

## 这条链路真正难在哪里

实时字幕的难点不在于把 WebSocket 接通，也不只在于选择一个 ASR 模型。真正困难的是同时维护三种一致性：

- 音频不能因为确认延迟、重连或背压而静默丢失；
- 字幕必须按照服务端确认的句子边界展示，不能让浏览器和后端各自猜测；
- 课堂结束后保存的内容必须和实时事件、录音文件以及后续分析保持可追溯关系。

一旦把这三件事放在一起，ACK、缓冲、窗口重叠、句子事件、翻译状态和最终整理就不再是零散功能，而是同一条数据链上的不同阶段。
